# 0009: Experiments: define, approve, run and read a comparison of setups

## Status

`implemented in 0.1.0` (approved by the owner 2026-09-29, with the answers in "Owner decisions" below). Revised
before approval: subjects that are code or programs, file inputs and outputs, measurements and the owner's
ratings.

## Context

Found while building StoryRoom (a OneShotStudio pipeline). Its first question is "which open-weight model
writes the best stories, with which settings and which prompt?". To answer it, StoryRoom grew its own
experiment code: a matrix of models × tasks, a runner, metrics, a judging step and reports, built on
hone-flow. Every pipeline (lyrics, music, images) will need the same thing, and none of it is specific to
stories: it is *generate candidates under different setups, score them on criteria, compare*. That is what
hone-select does for one task; an experiment does it for a set of test cases and keeps the comparison.

Not every experiment is about a model. The same shape answers code and tool questions: how Blender renders
an animation with different settings, which motion library suits the stories, how a JSON fixer behaves on
broken outputs, how well a custom voice exporter handles the outputs of different models. Those are custom
scripts and programs, with files as inputs and outputs, measured by code, by other programs or by a person.

The owner wants to **declare** an experiment in the project (test cases, criteria, models, parameters,
prompts, baselines), have hone-select create its folder and plan, **approve or deny** it in the dashboard,
then run it with one command, and read the results in the dashboard. No new pipeline per experiment.

## Problem

1. hone-select selects the best candidate for **one** task. It has no notion of a set of test cases, of
   setups compared across them, or of results that say "setup A beats setup B on criterion X".
2. A comparison costs hours of GPU or API money; nothing lets a person see the plan (how many calls, how
   long, how much) and approve it before it starts.
3. Each project writes its own runner, resume logic, judging and reports.

## Options

1. **Experiments in hone-select (proposed):** a declared experiment file, a plan, an approval, a
   resumable runner and results, all by hone-select, reusing its generators, gates, scorers, judges,
   budgets, records and dashboard.
2. Keep experiments in each project on hone-flow (what StoryRoom does now): repeated in every project; no
   approval step; not visible in the dashboard.
3. A separate honeworks package for experiments: one more package to install and keep in step, for
   something that is mostly hone-select's own pieces arranged differently.

## Decision

### 1. What an experiment is

| Term | Meaning |
|---|---|
| **Test case** | one input with an id: fields (a series brief, a song title) and / or files (a broken JSON, a scene file, another model's output) |
| **Subject** | what is being tested: a prompt to a model, a Python function, or any command or script (§2a) |
| **Factor** | one thing being compared: `model`, a parameter (`temperature`, `samples_per_pixel`), `prompt`, `library`, a script version: anything the subject receives |
| **Setup** | one choice for every factor (model = hemmingway-1, temperature = 1.0, prompt = guided) |
| **Baseline** | a named setup the others are compared against (for example today's choice) |
| **Criterion** | what is measured: a scorer (code, command, prompt judge), a gate, an automatic measurement (time, memory, exit code, file size) or a person's rating in the dashboard (§2b) |
| **Cell** | one setup on one test case, repeated `samples` times with different seeds |

### 2. Declared in the project

`hone-select experiments new "Open-weight writing"` creates the folder and a commented template:

```text
experiments/
  E0001-open-weight-writing/
    experiment.toml        the definition: written by a person, reviewed, committed
    cases/                 test cases (cases.toml, or one folder per case with its input files)
    prompts/               the prompt versions under test (guided.md, plain.md, ...), when the subject is a prompt
    scripts/               the scripts under test or used to measure, when they belong to the experiment
                           (they can also live anywhere in the project and be referenced by path)
    plan.json              generated by `plan`: every cell, the call count, time and money estimates,
                           and the hash of the definition it was made from
    review.json            approvals and denials: who, when, the note, the definition hash
    outputs/<case>/<setup>/<sample>/
      result.json          the output's data, measurements, scores and reasons (resumable: a cell with
                           this file is done)
      files/               the files it produced (a render, a WAV, the fixed JSON), and its log
    results/
      results.json         the numbers (per setup, per factor level, per criterion; baseline deltas)
      summary.md           the same as a readable table, with the chosen setup and why
```

Everything in the folder is committed, outputs and their files included: an experiment stays as evidence.
hone-select writes no `.gitignore`; a project that does not want some outputs in git ignores them itself.

```toml
# experiments/E0001-open-weight-writing/experiment.toml
title = "Open-weight writing"
question = "Which open-weight model, temperature and prompt write the best story premises?"

cases = "cases/"                        # or: cases = ["cases.toml"]; each case: id + fields for the prompts
samples = 2                             # outputs per cell (different seeds)
seed = 7

[generate]                              # how a candidate is made: the built-in prompt generator ...
kind = "prompt"
client = "hone_models:text"             # a TextClient factory (extra `models`), or any "module:factory"
prompt = "{prompt}"                     # the factor `prompt` picks a file from prompts/
output = "json"                         # text | json (with `schema = "module:Model"`)
# ... or your own code: generator = "story_room.writing:premises"   (called with the case and the setup)

[factors]
model       = ["gemma4-12b", "styletune-12b", "hemmingway-1", "muse-glimmer"]
temperature = [0.7, 1.0, 1.2]
prompt      = ["plain.md", "guided.md", "examples.md"]

[design]
kind = "full"                           # full: every combination | one_at_a_time: vary one factor
                                        # around the baseline | list: only the setups listed below
[[baseline]]
name = "today"
model = "gemma4-12b"
temperature = 0.8
prompt = "plain.md"

[criteria]                              # the same scorers, gates and judges as a selection.toml
gates   = ["valid_json", "five_premises"]
scorers = ["creativity", "unified_story", "clear_rule", "slop"]
weights = { creativity = 2, unified_story = 2, clear_rule = 1, slop = 0.5 }

[judges.astra]                          # prompt scorers use these; judges never see the setup
client = "hone_models:decision"
model = "astra"

[scorers.creativity]
kind = "prompt"
judge = "astra"
criteria = "The premise surprises: not the first idea anyone would have, and still makes sense."
output = "score"
scale = [1, 10]

[budget]                                # the run stops at the first limit (existing budget rules)
money_usd = 20
seconds = 36000

[run]
order = "by_model"                      # run all cells of one model before the next (fewer reloads)
concurrency = 1
```

Code scorers and gates (`slop`, `valid_json`) come from `registry = ["story_room.criteria"]`, as in a
selection today.

### 2a. The subject: a prompt, your code, or any program

`[generate]` names what is tested. Three kinds, the same experiment machinery for all:

| Kind | Declared as | Receives | Returns |
|---|---|---|---|
| `prompt` (built-in) | `kind = "prompt"`, a client factory, `prompt = "{prompt}"` | the case fields, the setup | the model's text or JSON |
| `python` | `kind = "python"`, `function = "story_room.motion:render"` | `(case, setup, ctx)`: `ctx.workdir` (a fresh folder for this sample), `ctx.seed`, `ctx.case_files` | data, or a `Candidate` with `files` |
| `command` | `kind = "command"`, `command = ["blender", "-b", "{case.scene}", "--python", "scripts/render.py", "--", "{setup_json}"]` | the arguments (with `{case.*}`, `{setup.*}`, `{workdir}`, `{seed}` filled in) and the same as JSON on stdin | files written to `{workdir}`, and optionally one JSON object on stdout (`data`, `measurements`) |

For every sample hone-select records, whatever the kind: **wall time, exit code / exception, peak memory,
the files produced (names, sizes, hashes) and the log** (stdout / stderr, capped). A failure is a result
(recorded, counted per setup), never a crash of the experiment. Each kind has a `timeout`; `retries`
applies to errors the subject marks as transient.

Options for programs that need care:

```toml
[generate]
kind = "command"
command = ["blender", "-b", "{case.scene}", "--python", "scripts/render.py", "--", "{setup_json}"]
timeout = 1800
wrap = ["scripts/gpu-lock.sh"]     # run inside a wrapper (the machine-wide GPU lock, a container, ...)
env = { BLENDER_USER_SCRIPTS = "scripts/blender" }
keep_files = "all"                 # all (default) | small (under 20 MB each, the rest hashed and deleted) | none
```

Examples of the non-AI experiments this covers:

| Experiment | Cases | Factors | Subject | Criteria |
|---|---|---|---|---|
| Blender render settings | 3 scene files | engine, samples, denoiser | `command`: blender with a render script | render time, peak memory, an image-quality scorer against a reference, owner rating |
| Motion library for stories | 5 story scenes | `library` = [a, b, c] | `python`: one adapter function per library | runs without error, smoothness metric, owner rating |
| JSON fixer | 40 broken outputs saved from real model calls | fixer version, strictness | `python`: the fixer | valid JSON, schema-valid, fields preserved (a code scorer comparing with the expected JSON), time |
| Voice exporter with different models' outputs | 10 lyric sheets | `source_model` (whose outputs are exported), exporter settings | `command`: the exporter | exit code, duration match, intelligibility (a Whisper command scorer), owner rating |

Cases can be the **outputs of an earlier experiment**: `cases = { from = "E0001", keep = "winners" }` turns
each case's best outputs (or all of them) into this experiment's input files, which is how "does the voice
exporter work with every model's output" is asked.

### 2b. Criteria that are code, programs or people

- **Code scorers and gates** (`registry = [...]`): any Python function of the candidate, which now also
  sees its files and measurements (`c.files`, `c.meta["measurements"]`).
- **Command scorers** (existing): any program; JSON in (the candidate, its file paths), a score out. A
  reference-image comparison, a Whisper intelligibility check or a unit-test run are command scorers.
- **Measurements as criteria:** `measure = { render_seconds = "lower", peak_memory_mb = "lower" }` turns an
  automatic measurement into a scored criterion (normalized across the experiment's samples).
- **People:** `[scorers.owner_look] kind = "human"` with a question and a scale. The dashboard shows each
  output (text, image, audio or video player, blind to the setup, in random order) and records the answer
  as a score. The results mark a human criterion as incomplete until enough outputs are rated
  (`min_ratings`), and the experiment can finish with the automatic criteria first.

### 3. Lifecycle

```text
new ──▶ draft ──plan──▶ proposed ──approve──▶ approved ──start──▶ running ──▶ completed
                          │  ▲                                 │   ▲
                        deny │ edit the definition             stop│  start again = resume
                          ▼  │ (the plan is made again)        ▼   │
                        denied                               stopped
```

| Command | What it does |
|---|---|
| `hone-select experiments new "<title>"` | creates `experiments/E000N-<slug>/` with a commented template |
| `hone-select experiments plan <EID>` | validates the definition (every scorer, judge, case and prompt exists), expands the cells, estimates calls, time and money (from the budget rates, or a 1-cell pilot with `--pilot`), writes `plan.json`; status `proposed` |
| `hone-select experiments approve <EID> [--note]` / `deny <EID> --note` | writes `review.json`; the same as the buttons in the dashboard |
| `hone-select experiments start <EID>` | runs an **approved** experiment whose definition still matches the approved hash (an edit needs a new plan and approval); skips cells already done, so it also resumes |
| `hone-select experiments stop <EID>` | stops after the current cell |
| `hone-select experiments status [<EID>]` | status, progress (cells done / total), money and time used |
| `hone-select experiments report <EID>` | (re)writes `results/` from `outputs/` |
| `hone-select experiments list` | every experiment in the project with its status |

### 4. How a run works (inside hone-select, no workflow to write)

For each test case, hone-select makes a **selection** exactly as today: the candidates are the cell
outputs (every setup × `samples`), produced by the subject (prompt, function or command) with the setup
as the variation
(`variation.params = {model, temperature, prompt}`), then gated, scored by the criteria and ranked. Each
case's selection is recorded in the span store with the experiment id and case in the trace context
(`hone.run_id = E0001`, `hone.item = <case>`), so the dashboard and hone-lens see every candidate, score and
reason. After the cases, the results are computed:

- per **setup**: mean total and mean per criterion with a 95 % interval (bootstrap over cases), gate pass
  rate, wins (best setup of a case), time and money per output;
- per **factor level** (for example every `model`, averaged over the other factors) the same numbers:
  "which model", "which temperature", "which prompt" are answered separately;
- against each **baseline**: the difference and whether its interval excludes zero;
- **judge agreement** when two judges score the same criterion (their difference per output).

Resume needs no workflow engine: a cell is done when its output file exists, and `start` skips done cells.
hone-select stays useful alone (no hone-flow dependency). Model clients stay behind the existing ports
(`TextClient`, `DecisionClient`), so local models, AvalAI and fakes work the same way; `order = "by_model"`
lets a local client load one model at a time.

### 5. In the dashboard

A new **Experiments** page next to Runs, reading `experiments/` from the working directory
(`hone-select dashboard --project .`):

- **List:** EID, title, status, progress, cells, estimated and used time / money, last change.
- **Rate:** the blind rating screen for `human` criteria: one output at a time (text, image, audio or
  video), the question and the scale; progress per criterion.
- **An experiment:** the question, the definition (cases, factors, baselines, criteria, judges), the plan
  (the cell matrix, estimates), and **Approve / Deny** buttons with a note (only while `proposed`). The
  buttons write `review.json` exactly like the CLI; the page shows who decided and when.
- **Results** (running or completed): the setup table (filterable, sortable, best first), one table per
  factor with each level's numbers and interval, the baseline comparison, and a link from every number to
  the outputs behind it (case → candidates → reasons, the existing run page).

The dashboard stays on localhost. Its only writes are Approve / Deny (`review.json`) and ratings
(`ratings.jsonl` in the experiment folder); a request must come from the page itself (same-origin check).
Output files are served read-only from the experiment folder.

## Consequences

- One declared file per experiment instead of a runner per project; every experiment has the same folder,
  plan, approval and results, and shows in the dashboard.
- Nothing expensive starts without a person approving a plan with its estimates; an edited definition
  needs a new approval.
- StoryRoom's own screen, judging and report code is replaced by an experiment definition (its C3 screen
  becomes `E0001`), and the other pipelines get the same tool.
- The same tool answers code and tool questions (Blender settings, libraries, fixers, exporters), with
  files in and out, automatic measurements, program scorers and the owner's ratings.
- hone-select grows by an experiment module (definition, plan, runner for the three subject kinds,
  results), a CLI group and two dashboard pages: roughly 1,200–1,500 lines.
- Running arbitrary commands is what the owner asks for, and it runs with the user's own rights: a
  definition is code. That is one more reason nothing starts before a person approves the plan, and the
  plan shows the exact commands. The results statistics stay simple (means, bootstrap intervals,
  win counts); anything more (significance testing across many factors, adaptive designs) is left out.
- Full designs grow fast (4 models × 3 temperatures × 3 prompts × 8 cases × 2 samples = 576 outputs);
  the plan shows the count and cost before approval, and `one_at_a_time` or `list` designs keep it small.

## Migration and compatibility

Additive: new commands, a new module and a new dashboard page. Selections, configs and the span store are
unchanged; experiment runs are ordinary selection runs with the experiment id in their trace context.
StoryRoom moves its C3 screen to `experiments/E0001-...`; the partial C3 run stays in its run folder as
history.

## Owner decisions (2026-09-29)

1. **Outputs are committed:** experiments stay in git with their outputs, unless the project ignores them.
2. **Default design:** `full` (every combination); the plan shows the size before approval.
3. **The pilot:** `plan` measures time and cost only with `--pilot`.
4. **Output files:** all kept by default (`keep_files = "all"`).
